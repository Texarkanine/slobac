# Prior Art on Weak String Assertions Against Runtime-Emitted Output

## TL;DR
- **The phenomenon is not named as a distinct test smell** in any academic catalog, book, or linter rule. It sits in a genuine *missing middle* between two named poles — "over-specified presentation oracle" (Sensitive Equality / Fragile Test) and "vacuous/tautological assertion" — and is best described as an **unintentionally partial oracle** (Barr et al.'s "partial oracle" language) that produces **false confidence**. The nearest *named* thing is the industry proverb "error strings are not part of the API" (Go community) and the tooling response to it (Node.js ERR_ codes, eslint-plugin-jest `require-to-throw-message`).
- **The false-confidence angle is best sourced from three literatures**: (a) test-oracle/oracle-quality research (Barr et al. 2015 "partial oracle"; Schuler & Zeller "checked coverage"; the "oracle deficiency"/weak-assertion strand); (b) mutation-testing practice (string-literal mutators survive when output is emitted but never semantically asserted); and (c) the Go/Node.js "error strings are not API" war stories (Hyrum's Law ossification).
- **The consensus recommendation hierarchy is: assert on typed errors + structured properties (error codes, error enums, `errors.Is`/`errors.As`) > assert on structured log/event fields > match message substrings** — and text asserts are legitimate only where the emitted text *is the product* (compiler/CLI diagnostics via golden/snapshot files), for i18n, or where a downstream contract parses the text. The `match=`/`toThrow(/regex/)` norm is **tolerated pragmatism, explicitly hedged in official docs**, not endorsed best practice.

## Key Findings

**1. Is it named? No — but the negative space is well-mapped.** No test-smell catalog (testsmells.org / van Deursen et al. 2001 / Garousi & Küçük / Meszaros's 18 smells) names "a substring assertion on emitted text that is too weak to lock meaning." The closest named neighbors each capture only *part* of it:
- **Sensitive Equality** (van Deursen et al. 2001; refined by Meszaros as a *cause* of **Fragile Test**) — asserting on `toString()`/rendered text. This captures the *presentation-coupling/brittleness* facet but is explicitly about *over-specification* (too strong), the opposite of the false-confidence facet.
- **Assertion-free / Unknown Test** and **tautological assertions** (Mark Seemann, ploeh blog) — capture the *vacuous* pole (no real check). A `toContain("phrase")` assertion is *not* vacuous — it runs and can fail — so it escapes this category.
- **Assertion Roulette** — explicitly a *different* thing (multiple asserts without failure messages); keep distinct, as the brief notes.

**2. The academic hook for the false-confidence angle is the "partial oracle."** Barr, Harman, McMinn, Shahbaz & Yoo, *The Oracle Problem in Software Testing: A Survey* (IEEE Transactions on Software Engineering, vol. 41, no. 5, pp. 507–525, May 2015; DOI 10.1109/TSE.2014.2372785) formalizes a test oracle as a *partial* function and defines a **partial oracle** as one that "specifies important (but not complete) properties of the SUT." The paper's Definitions 2.6–2.8 (open-access PDF at discovery.ucl.ac.uk/id/eprint/1471263) define the Ground Truth oracle plus the **soundness** and **completeness** of a test oracle — precisely the vocabulary needed to describe the subject phenomenon. A substring match on an error message *is* a partial oracle: it is *incomplete* (does not pin the full property) and often *unsound* against the intended property (green for text with the opposite meaning). The literature treats partiality as a deliberate engineering compromise; the brief's specific interest — *unintentionally* partial oracles that create false confidence — is not called out under its own name, but the machinery to describe it lives here.

**3. Oracle-quality metrics directly target this failure.** Schuler & Zeller, *Assessing Oracle Quality with Checked Coverage* (ICST 2011; extended as *Checked coverage: an indicator for oracle quality*, Software Testing, Verification and Reliability 23(7):531–551, 2013) introduce **checked coverage**: the fraction of executed statements that actually influence a value that reaches an oracle. Their motivating example is a test that executes a parser but "no test ever actually checks whether the parser works." A `toContain` on a message is exactly this: the code path runs and the message is produced, but the *semantic claim* is not in the checked slice. The 2013 abstract states verbatim: "Our experiments on seven open-source projects show that checked coverage is a sure indicator for oracle quality — and even more sensitive than mutation testing, its much more demanding alternative." A follow-on survey (arXiv:2212.06118) quantifies that on average 24% of executed statements do not influence any oracle.

**4. Mutation testing is the empirical detector.** Practitioner and tool sources are consistent: **a surviving string-literal mutator means "you are executing code whose output you never assert."** Stryker ships a string-literal mutator; the guidance is that "the most common reason mutants survive is weak assertions." The academic strand (e.g., *Assertion Inferring Mutants*, arXiv:2301.12284) uses mutation to *discard weak assertions* — defined there as "assertions that are trivial to satisfy and would not trigger any error if the target class C had incorrect behaviour." This is the formal analog of the brief's canonical example.

**5. The strongest *named industry position* is Go's "error strings are not part of the API."** This is the most direct, most-cited prior art against the whole class:
- **Dave Cheney, "Don't just check errors, handle them gracefully"** (dave.cheney.net, April 27, 2016; drawn from his GoCon Spring 2016 Tokyo talk) — the canonical proverb-level statement: *"comparing the string form of an error is, in my opinion, a code smell, and you should try to avoid it."* He adds the deeper principle: *"The Error method on the error interface exists for humans, not code… You shouldn't try to change the behaviour of your program by inspecting it,"* and even argues type assertions are no safer: *"Callers should feel no more comfortable asserting an error is a particular type than they would be asserting the string returned from Error() matches a particular pattern."*
- **Go Wiki: Go Test Comments** (go.dev/wiki/TestComments) — official style guidance, verbatim: *"Since this has the potential to turn your unit test into a change detector, don't use string comparison to check what type of error your function returns. It's OK to use string comparisons to check that error messages coming from the package under test satisfy some property, for example, that it includes the parameter name."* This *carves the legitimate exception* precisely.
- **golang/go #49356** — a proposed `errorstringcompare` analysis pass to warn when code compares against `Error()` strings (including `strings.Contains`, `HasPrefix`, regex), with the rationale that "Go 1 and the Future of Go Programs does not explicitly promise that error strings are protected."
- Recommended alternative: `errors.Is` / `errors.As` (Go 1.13, go.dev/blog/go1.13-errors) and typed error structs with fields (Learn Go with Tests).

**6. Node.js is the canonical ossification war story.** Node core added machine-readable `ERR_` codes (tracking issue nodejs/node #11273, "Tracking Issue: Migrate errors to internal/errors.js," created by James Snell on Feb 9, 2017 after PR #11220 landed the `internal/errors.js` mechanism) precisely because userland and tests matched *message strings*, so messages could not be improved without ecosystem breakage; the migration was treated as **semver-major**. The authoritative "why" is the Node.js Collection blog post *"Node.js Errors — Changes you need to know about"* by Michael Dawson (Node.js Runtime Tech Dev @ IBM), which states plainly: "This will impact any user whose code parses the message strings," and, "Once Error codes are in place the plan is to be able to update message strings without having to mark the change as SemVer major." The current Node.js API docs (nodejs.org/api/errors.html) now state verbatim: *"The error.code property is a string label that identifies the kind of error. error.code is the most stable way to identify an error. It will only change between major versions of Node.js. In contrast, error.message strings may change between any versions of Node.js."* (First landed in commit 5fae450 / PR #24090, fixing issue #23975.) This is Hyrum's Law made concrete — and Go's stdlib carries the same scar tissue: `net/http`'s `MaxBytesError.Error()` (src/net/http/request.go, added via golang/go #49359) reads `func (e *MaxBytesError) Error() string { // Due to Hyrum's law, this text cannot be changed. return "http: request body too large" }`.

**7. Framework docs frame message-matching as hedged pragmatism, not best practice.**
- **eslint-plugin-jest `require-to-throw-message`**: exists because `toThrow()` with no argument "will pass for any thrown error" — a rule specifically against the *vacuous* end. Note it only requires *a* message, not a semantically locking one.
- **RSpec `raise_error`** without an argument emits a runtime **warning**: "Using the `raise_error` matcher without providing a specific error or message risks false positives, since `raise_error` will match when Ruby raises a `NoMethodError`, `NameError` or `ArgumentError`, potentially allowing the expectation to pass without even executing the method you are intending to call." RSpec actively discourages the vacuous form.
- **pytest `raises(match=)`**: docs describe it as a regex *search* against the message; community/tutorial framing is explicit that "the text of an error message is rarely part of the public interface, so tests that rely on it tend to be flaky." pytest warns that matching against an empty string "will *always* pass," and the `pytest-raises` docs note that with a plain substring "if the message is 'too simple' you may get false positives."
- **Google Testing Blog**: "Change-Detector Tests Considered Harmful" (2015) and "Prefer Narrow Assertions in Unit Tests" (2024), plus *Software Engineering at Google* ch. 12, frame brittleness — but Google's line is about *over-broad* assertions; it does not name the underdetermined-substring case.

**8. Legitimate text-assert cases are drawn where the message IS the product.** Rust compiler UI tests snapshot the full `.stderr`/`.stdout` via `--bless` (rustc-dev-guide); dtolnay's `trybuild` and oli-obk's `ui_test` do the same for macro/diagnostic crates, explicitly on the grounds that "the errors are also part of public API." This is the **snapshot/approval-testing** alternative (Llewellyn Falco's ApprovalTests / Emily Bache) as an *explicit presentation contract* — the whole rendered output is the oracle, human-reviewed and diffed, rather than a lone substring pretending to encode meaning.

## Details

### The taxonomy verdict (Question 5): a genuine missing middle
Map the phenomenon on two axes — *assertion strength on presentation* and *semantic determination*:

- **Sensitive Equality / Fragile Test**: strong on presentation (full string / `toString`), so brittle; but at least the exact string does pin behavior. Named. (van Deursen 2001; Meszaros — whose JAOO 2009 slides note "Sensitive Equality is really a cause of Fragile Test.")
- **Assertionless / Unknown Test / tautological assertion**: no semantic determination and effectively no presentation check. Named. (van Deursen; Seemann's ploeh blog "Tautological assertion," 2019.)
- **The subject phenomenon**: *weak* on presentation (a substring/regex), so it *looks* robust to rewording, yet *underdetermines semantics* — it passes for text with the opposite meaning. It is neither fully brittle nor fully vacuous. **There is an assertion, so it evades the vacuous/tautological label; it is loose, so it evades Sensitive Equality; it is still presentation-coupled, so it inherits Fragile Test's ossification risk.** That intersection is unoccupied in every catalog reviewed.

**Verdict: this deserves explicit treatment as a named sub-smell, but the honest finding is that it currently lives implicitly, split across three homes** — "partial/weak/incomplete oracle" (academic, Barr et al.; Schuler & Zeller), "change-detector test / error-string coupling" (Go Wiki + Google), and "vacuous `toThrow`" (linter rules). A useful coinage would be something like *"underdetermined output oracle"* or *"semantically-loose message pin"*; no source uses such a term today. The requester's suspicion — that it is a missing middle rather than a specialization of an existing smell — is correct.

### The recommendation hierarchy (Question 3), from strongest evidence
1. **Assert on error *type* + structured properties.** Go's `errors.Is`/`errors.As` and typed error structs; Node's `err.code` (ERR_ codes); Rust's error enums matched exhaustively; custom exception classes in Python/JS with `.code`/fields. Rationale is unanimous across Go Wiki, Cheney, Node API docs, Learn Go with Tests: the type/code is the stable machine contract; the message is for humans.
2. **Assert on structured log/event fields, not the rendered line.** structlog's `capture_logs`/`LogCapture` yields event dicts (`{'event': 'hello', 'log_level': 'info', ...}`); pytest-structlog's `log.has("event", key=value)` asserts on event name + level + bound context, not formatted text. Same philosophy in the zap/serilog ecosystems. This encodes the semantic claim (which event, what level, what fields) instead of the presentation.
3. **Assert on the causing state change/behavior** rather than the message at all (Google's "test behavior, not implementation"; Seemann's state-based testing).
4. **If the text itself must be verified, make it an explicit presentation contract** via golden-file/approval/snapshot testing (ApprovalTests, insta, rustc `--bless`), reviewed and diffed as a whole — not a lone substring.
5. **Substring/regex message match** is the *bottom* of the hierarchy: acceptable as a *supplementary* check that a dynamic message includes a specific datum (e.g., the offending parameter name), per the Go Wiki carve-out, but not as the primary oracle for the behavior.

### When text asserts are enough (Question 4)
- **The message is the product**: compiler/linter/formatter diagnostics (Rust UI tests, clang `-verify`, Elm's error-message culture), CLI UX copy. Here the rendered output is the specified behavior; snapshot the whole thing.
- **Localization/i18n**: verifying the right message key/catalog entry renders.
- **Parse contracts**: when a downstream system genuinely parses log lines or messages (log format as API) — though the mature move is to make that an explicit structured contract.
- **Regulatory/audit** requirements that mandate specific wording.

### Reading the `match=`/`toThrow(/regex/)` norm (Question 6)
**Tolerated pragmatism, explicitly hedged — trending toward mild criticism.** Evidence: eslint-plugin-jest and RSpec both ship guardrails against the *vacuous* form (require a message; warn on bare `raise_error`), which shows the ecosystem recognizes the weak-oracle risk at the extreme. But none of these tools pushes toward *type/code* assertions as the default; the message argument is treated as sufficient. pytest's own community docs concede message text "is rarely part of the public interface, so tests that rely on it tend to be flaky." JUnit's `assertThrows` returning the exception object for further inspection is a design signal that the *intended* next step is asserting on typed properties, not the message string. So the norm is a convenience that framework authors accommodate while quietly warning against over-reliance — not something any official source holds up as the right way to lock behavior.

## Recommendations
1. **Adopt a local naming + lint policy now.** Treat "substring/regex assertion on emitted text as the *primary* oracle for a behavior" as a reviewable smell. In JS/TS, enable eslint-plugin-jest `require-to-throw-message` (kills the vacuous `toThrow()` end) but pair it with a code-review rule that a message match must be *accompanied by* an error-type/`code` assertion. In Go, adopt the Go Wiki guidance and consider an `errorstringcompare`-style vet check (golang/go #49356).
2. **Push assertions up the hierarchy.** Require typed errors with codes/fields as the assertion target; reserve message matching for verifying a *dynamic datum* is present (the Go Wiki carve-out), never for identifying *which* error/behavior occurred.
3. **Convert log-line asserts to structured-field asserts** (structlog/pytest-structlog `log.has(...)`, or equivalent) wherever logs are tested.
4. **Where the text is the product, switch to golden/approval/snapshot files** reviewed as a whole (ApprovalTests, insta, `--bless`), so the presentation contract is explicit and diffable rather than a fragile substring.
5. **Run mutation testing (Stryker/PIT/mutmut) as the objective check.** A surviving string-literal or message mutant is direct evidence that an emitted-output assertion underdetermines meaning. Use survivors as the prioritized hardening list. **Benchmark that would change the recommendation:** if mutation testing shows message-substring asserts are *killing* the relevant behavioral mutants (i.e., the substring genuinely pins the semantics for that code path), the assertion is adequate and no change is needed.
6. **Guard against ossification (Hyrum's Law).** Treat any message text that tests or userland pin as a de-facto public contract; if you don't want that, don't let tests pin it — assert the code/type instead. Node's ERR_ migration and Go's `// Due to Hyrum's law, this text cannot be changed` comment are the cautionary precedent.

## Caveats
- **No source names the exact phenomenon**; this brief assembles the nearest-neighbor map rather than reporting an established term. The "unnamed" finding rests on absence across the reviewed catalogs (testsmells.org, van Deursen 2001, Meszaros's 18 smells, tsDetect literature) — comprehensive coverage, but still absence of evidence rather than proof of absence.
- **The academic "partial oracle" / "weak assertion" literature is about oracles generally**, not specifically about runtime-emitted *text*; applying it to the message/log/CLI surface is my synthesis, not a claim those papers make explicitly.
- **The Node.js #11273 issue body itself is a terse tracking checklist**; the full "why" (messages were being depended upon) is authoritative in the associated Node.js Collection blog post (Michael Dawson) and current API docs, not in the issue prose. The exact publication date of that blog post was not pinned down (≈2017, Node v8→v9 era).
- **Framework-doc framing is inferred from official docs plus high-quality community posts**; where I call the `match=` norm "tolerated pragmatism," that is a reading of the evidence, not a direct quote from pytest/Jest maintainers stating that stance.
- Several supporting sources are secondary (blog posts, tool guides); the primary anchors (Barr et al. 2015; Schuler & Zeller 2011/2013; Go Wiki; Node API docs; RSpec/Jest docs; rustc-dev-guide) are authoritative.
