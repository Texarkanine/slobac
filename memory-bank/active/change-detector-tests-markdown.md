# Prior Art on "Prose-as-Oracle" Tests: Automated Tests That Assert on Committed Documentation

## TL;DR
- **There is no canonical name for this exact phenomenon.** The best characterization is that it is a *specialization of two well-established test smells applied to a new surface*: Google's **change-detector test** (fails on any edit, verifies nothing behavioral) crossed with the van Deursen/Meszaros **Sensitive Equality / Fragile Test** family (coupling the test to an incidental string representation), plus a **tautological/weak-assertion** flavor for the positive `assert "X" in text` shape. Your working labels ("code that tests prose," "documentation-pin tests," "prose-as-oracle") are not in the literature, but they name a real gap.
- **The agent-skill surface (SKILL.md / AGENTS.md / CLAUDE.md as executable interface) is genuinely novel territory (2024–2026).** No test-smell taxonomy, xUnit pattern, or linter catalog addresses "markdown consumed as a program by an LLM agent." The nearest analogs are the **prompt-regression / eval** literature (promptfoo) and the brand-new **agent-harness linter** category (AgentLinter, AgentLint, cclint) — none of which frames itself in test-smell terms.
- **The literature's fix is consistent:** don't assert prose substrings from your unit suite. Either (a) delete the test, (b) move it to a docs-linter tier (Vale/markdownlint) run separately, (c) encode the *real* invariant in code, or (d) generate the docs from code so the check becomes a generator/snapshot contract. The one defensible case for a mechanical forbidden-token scan is when the markdown **is** the public interface — i.e., an architectural fitness function for prose.

## Key Findings

1. **Closest named smell — "Change-Detector Tests" (Google).** The canonical write-up is the Google Testing Blog "Testing on the Toilet: Change-Detector Tests Considered Harmful" (Jan 2015). Notably, this is a jokey *internal* Google term, and its original scope is narrower than the documentation case: per *Software Engineering at Google*, ch. 13 (abseil.io), "Some people at Google jokingly refer to tests that overuse interaction testing as change-detector tests because they fail in response to any change to the production code, even if the behavior of the system under test remains unchanged." A documentation-pin test is a textbook instance of the *symptom* the term describes — it fails when markdown wording changes, regardless of whether the product still works — even though the coinage was about mock-heavy interaction tests, not prose. The concept is reinforced in Goran Petrovic's SE-Radio interview (Ep. 632, Sep 2024), which frames change-detectors via mutation testing.

2. **Root-cause smell — "Sensitive Equality" / "Fragile Test" (van Deursen et al. 2001; Meszaros, *xUnit Test Patterns*, 2007).** Meszaros explicitly notes "Sensitive Equality is really a *cause* of Fragile Test." Sensitive Equality is defined as tests that couple to a string/`toString()` representation and "depend on many irrelevant details, such as commas, quotes, and spaces." Documentation-pinning is Sensitive Equality generalized from `toString()` output to a committed `.md` file: the test binds to incidental wording rather than a semantic contract. The smell originates in the seminal test-smell paper (van Deursen, Moonen, van den Bergh, Kok, "Refactoring Test Code," 2001) and is a detected smell in tsDetect and xNose today.

3. **The weak-positive-assertion flavor — "Tautological" / "weak assertion" tests.** A positive `assert "X" in text` is often too weak to verify the procedure it claims to protect. Mark Seemann's "Tautological assertion" (ploeh blog, Oct 2019; follow-up Dec 2025) documents assertions "written in such a way that [they] can't possibly fail." The 2026 practitioner discussion of AI-generated tests (qaskills.sh, getautonoma.com) catalogs "weak assertions … like toBeDefined, not None, or length > 0 that tolerate wrong values" — the same failure mode as `assert phrase in readme`.

4. **The academic taxonomy has no entry for this.** Garousi & Küçük's "Smells in software test code: A survey" (JSS vol. 138, 2018, pp. 52–81, doi:10.1016/j.jss.2017.12.013) is the largest catalog: the authors "proposed a public test smell classification board for 196 test smells extracted from 166 sources (120 gray literature and 46 formal)." Nothing in it concerns asserting on committed documentation. The testsmells.org catalog (Peruma et al., tsDetect) lists Assertion Roulette, Sensitive Equality, Eager Test, Mystery Guest, Resource Optimism, etc., but no "documentation oracle" smell. This confirms the specific phenomenon is **unnamed** in the formal literature.

5. **Adjacent industry critiques converge but don't name it.** Kent C. Dodds ("Testing Implementation Details," "Avoid the Test User," "Effective Snapshot Testing") and Justin Searls ("Please Don't Mock Me," Assert.js 2018) both attack tests that break on refactors without behavioral change — the same disease, different organ. Snapshot-testing criticism ("nuke the snapshot and record a fresh passing one") is the closest behavioral cousin: a doc-keyword checklist is effectively a hand-rolled snapshot test over prose.

6. **The legitimate case is real and has a name-adjacent framing: architectural fitness functions.** Ford/Parsons/Kua's *Building Evolutionary Architectures* (O'Reilly 2017; 2nd ed. 2023 adds Pramod Sadalage) states: "An architectural fitness function provides an objective integrity assessment of some architectural characteristic(s)." ArchUnit-style *negative* rules ("classes in package X must not depend on Y") are the code analog of "SKILL.md must not contain `uv run`." When the markdown **is** the interface — a wrapper skill that an LLM executes — a forbidden-token scan is a fitness function on the public contract, not a documentation-pin. That is the line the literature would draw.

## Details

### The stockroom corpus (concrete grounding)
`Texarkanine/stockroom` (public, AGPL-3.0, ~36 commits, v0.4.0 released Jul 11 2026) is a "dual-manifest plugin" shipping a shared `skills/` tree consumed by both Cursor and Claude Code. It is 81.5% Python / 14% JavaScript, and the Makefile confirms the test tooling: `test: sync test-js` runs `uv run pytest` plus `node --test tests-js/*.test.mjs`; the full CI gate is `ci: sync lock-check lint format-check test reuse`. The engine lives under `skills/sr-search/`, and the skill bodies (`sr-initialize`, `sr-search`, `sr-query`, `sr-semantic`, `sr-dashboard`) are the shipped SKILL.md files. This is exactly the environment your five shapes describe: a Python CLI (with real `uv run`, `PYTHONPATH=…/src`, and `python -m stockroom` invocations visible in the Makefile) wrapped by SKILL.md files that must *not* leak those raw internals to the agent — which is precisely why a forbidden-token scan on the wrapper prose is tempting. (Note: GitHub's robots policy blocked deep directory/file listing of the test files themselves, so the taxonomy of individual asserts below is reconstructed from the five shapes you supplied plus the confirmed pytest tooling, not from line-level reading of each test.)

### Mapping your five shapes to the literature
1. **Forbidden-token scan** (`SKILL.md must not contain uv run/PYTHONPATH/python -m`) → **negative architectural fitness function** applied to prose. *Potentially legitimate* when the SKILL.md is the executable interface; the invariant "the agent-facing contract must not expose raw internals" is a real behavioral property. Weakness: it is a proxy. It verifies the string is absent, not that the wrapper actually works when invoked.
2. **Docs keyword checklist** (`docs/foo.md must contain phrases`) → **Sensitive Equality + change-detector**. Weakest form. Green means "strings still present," not "procedure correct."
3. **Order pin** (command A before command B in prose) → **change-detector** with a **Sensitive Equality** ordering dependency; directly analogous to snapshot-testing element ordering. Breaks on pure editorial reordering.
4. **Feature-doc completeness** (after shipping `--detail raw`/`--format json`, assert skill mentions them) → **change-detector**; a "the docs mention the flag" proxy for "the flag works." The literature's verdict: test the flag's behavior, not its mention.
5. **Vacuous packaging smoke** (front-matter has non-empty name/description) → **tautological / weak assertion** bordering on a schema check. This one is defensible *if reframed as schema validation* (the SKILL.md front-matter is a machine-parsed manifest), which is closer to a docs-linter/JSON-schema check than a prose oracle.

### Explicitly-separated cousins (per your out-of-scope list)
- **Doctest / docs-as-tests / executable specs** (`pytest-markdown-docs`, `markdown-pytest`, `pytest-readme`, `phmdoctest`; Manny Silva's *Docs as Tests* book and docsastests.com) — these *run* the code in the docs. That is the healthy inverse of prose-pinning: the doc drives real execution, so a pass means the example works. docsastests.com's own framing is instructive: "each doc is a test suite, each procedure a test case, each step an assertion" — but crucially "tests run against the product … not against mocks. Not against code."
- **Doc linters** (Vale, markdownlint, proselint, link checkers) — validate docs *as docs*. Vale supports banned-word/prohibited-term rules — meaning a forbidden-token scan *belongs in a Vale rule*, not a unit test. GitLab's docs pipeline (separate `docs-lint` job; Vale at `error` level only for brand/render-breaking issues) is the reference implementation of tiering these separately.
- **Presentation-coupled tests / CLI help greps** — pin runtime strings from a running SUT, not committed markdown.
- **Snapshot/golden testing of generated docs** — a generator contract, not a hand-authored README pin.

### The agent-skill novelty
SKILL.md (Anthropic, GA late 2025), AGENTS.md, CLAUDE.md, and `.cursorrules` are all 2024–2026 conventions where **prose is the program**. AGENTS.md's trajectory shows how fast this is moving: on Dec 9, 2025 it was donated by OpenAI to the Linux Foundation's new Agentic AI Foundation (AAIF) — co-founding it alongside Anthropic's MCP and Block's goose — and per the Linux Foundation it "has already been adopted by more than 60,000 open source projects and agent frameworks including Amp, Codex, Cursor, Devin, Gemini CLI, GitHub Copilot, Jules and VS Code." Testing practice for these files is nascent and lives in two non-overlapping worlds that have *not* been connected to the test-smell literature:
- **Prompt/eval regression** (promptfoo — founded 2024 by Ian Webster & Michael D'Angelo; OpenAI announced its acquisition March 9, 2026, subject to closing conditions, citing 350k developers and use at "more than 25 percent of Fortune 500 companies"): assertions like `contains`, `not-contains`, `llm-rubric`, and `factuality` run against the *model output produced from* the SKILL.md, not against the file's bytes. Promptfoo's own repo ships a `promptfoo-evals` SKILL.md advising "deterministic assertions where possible, model-graded only when needed." This is the right way to test a skill: run it, judge the behavior.
- **Agent-harness linters** (AgentLinter, AgentLint, cclint) — lint CLAUDE.md/AGENTS.md/skill front-matter for structure, secrets, contradictions, and file length. These are docs-linters for agent prose, i.e., exactly where a forbidden-token or schema check should live.

Anthropic's own guidance ("Equipping agents for the real world with Agent Skills," and the skill-creator SKILL.md) tells authors to test skills by **running representative tasks and evaluating outcomes** (LLM-as-judge, blind A/B comparators), never by asserting on the skill file's text. That is the strongest available signal that byte-level prose assertions are off-pattern even inside the agent-skill community.

## Recommendations

**Stage 1 — Triage each prose-asserting test by asking "would this fail if the product broke, and pass if only wording changed?"** If a doc edit for clarity fails CI with no behavioral change, it is a change-detector test. Delete shapes #2, #3, and #4 outright unless they can be re-grounded (below). This is the fastest win and matches Google/Meszaros guidance directly.

**Stage 2 — Re-ground the survivors on the real invariant.**
- Shape #4 (feature completeness): replace "skill mentions `--format json`" with a test that *invokes* the CLI with `--format json` and asserts valid JSON — an executable check, not a mention check.
- Shape #5 (front-matter): reframe as **schema validation** (name/description present, non-empty, within length limits). Move it out of the unit suite into a manifest-validation step; this is legitimate and cheap.

**Stage 3 — Tier docs checks separately from unit tests.** Move any surviving prose checks into a dedicated `docs-lint` job using Vale (for banned/required terminology) and markdownlint (structure). Run it as its own CI gate so a wording change never turns the unit suite red. GitLab's split is the template.

**Stage 4 — Keep the forbidden-token scan (shape #1) only if you treat it as a fitness function on the public interface, and make it behavioral where possible.** The rule "wrapper SKILL.md must not contain `uv run` / `PYTHONPATH` / `python -m`" is defensible *because the SKILL.md is the contract an LLM executes* — leaking raw internals is a genuine interface regression, analogous to an ArchUnit forbidden-dependency rule. Strengthen it two ways: (a) express it as a negative-grep fitness function documented as such (with a rationale comment like ArchUnit's `.because()`), and (b) back it with at least one promptfoo-style eval that actually runs the skill and asserts the agent uses the on-path `stockroom` shim rather than raw `python -m`. That converts a proxy into a behavioral guarantee.

**Benchmarks that would change the recommendation:** If a mutation-testing or "invert the assertion" check shows a prose test *does* catch real regressions the code suite misses (rare), keep it. If the SKILL.md is generated from code, convert the check to a generator/snapshot contract and stop hand-pinning. If a skill is not actually executed by an agent (pure human docs), every prose assertion should move to the docs-lint tier.

## Verdict on the honest gap statement
Against your four options, the evidence supports **(c) with a strong dose of (d)**: this is a **specialization of existing smells — change-detector + Sensitive Equality/Fragile Test, with a tautological-assertion sub-case — applied to committed markdown**, and *simultaneously* the agent-SKILL.md variant is **mostly undocumented territory**. It is *not* (a) a known named smell, and *not* merely (b) a rename — the committed-documentation-as-oracle framing genuinely extends the classic smells to a surface they were never written for. A crisp coinage ("prose-as-oracle" or "documentation-pin test") fills a real terminological gap and is defensible as a named specialization.

## Caveats
- **No line-level confirmation of the stockroom tests.** GitHub's robots policy blocked automated reading of the repository's test directory and individual test files; the framework (pytest + `node --test`), the CI gate, and the skill/engine layout are confirmed from the README and Makefile, but the specific asserts are mapped from the five shapes you provided, not read verbatim. A local `grep -rn "SKILL.md\|README\|assert.*in " skills/*/tests` (or the JS test dir `skills/sr-search/tests-js`) would confirm counts.
- **"Change-detector" and "Sensitive Equality" are the nearest names, not exact matches.** Change-detector was coined for mock-heavy interaction tests, and Sensitive Equality for `toString()`-coupled assertions; neither targets committed-markdown oracles. Applying them is an informed extrapolation.
- **The agent-skill testing field is moving fast (2025–2026) and much of the source material is vendor blogs and practitioner posts, not peer-reviewed.** The promptfoo/OpenAI acquisition (announced, not yet closed as of Mar 9 2026), the AAIF donation of AGENTS.md, and the harness-linter tools are all very recent; treat specifics as current-as-of mid-2026 rather than settled.
- **Some cited 2026 practitioner sources (qaskills.sh, getautonoma, agentlinter.com) are commercial/SEO content.** Their framing of weak-assertion and tautological anti-patterns is consistent with the primary sources (Seemann, Google, Meszaros), but they are corroborating, not authoritative.
